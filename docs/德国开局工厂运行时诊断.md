# 德国开局工厂运行时诊断

本文记录临时运行诊断和随后补齐开局 OOB 的修复。2026-09-07，用户已确认德国补齐 OOB 后解决工厂不计数问题，并要求推广至所有国家。现已为项目全部 349 份国家历史配置 OOB 入口；不改变工厂、地区修正、领土、经济平衡，也不向存档添加持久诊断变量。

## 记录内容

玩家控制德国时，在 GFCC 地区系统开局初始化前后，以及每个游戏日，向游戏用户目录的 `logs/game.log` 写入 `APDC_FACTORY_DIAG:` 行。`stage=0/1/2` 分别表示初始化前、初始化后、每日采样。每日只遍历德国控制的地区，不为其他国家重复执行。

- `GER_SUMMARY`：国家统计的民工/军工、可供新建造项目使用的民工、所控制地区的工厂合计及未损坏合计。
- 地区记录：地区 ID、所有者、是否德国核心、民工/军工、损坏与未损坏数量、`local_factories`、污染度、安全度、重建度。
- 开局记录所有受控地区；之后只记录有民工或军工的地区。

不直接断言“地区合计必须等于国家数量”：占领、修正等可以造成合理差异，必须结合前后变化判断。国家脚本统计也不是引擎内部缓存的直接转储。

## 能区分什么

1. 地区数量增加、国家脚本统计不增加：问题不只是顶栏文本显示；继续定位国家计数/可用工厂计算。
2. 地区数量和国家脚本统计都增加、界面仍旧：进一步检查界面或其所读取的统计口径。
3. 损坏数量或本地工厂修正同时变化：检查这些因素是否能解释差额。
4. 读档前后建筑和修正不变、国家统计变化：获得存档文件本身不能提供的运行时差异。

日志不会单凭一次差异就确认 GFCC 是根因。该系统的数值和初始化顺序均未改动。

## 采样限制

- 新增脚本需重新启动游戏才能可靠加载。之后正常游玩德国即可自动记录，不要求专门再做一轮相同操作。
- 每日采样不等于逐次施工回调；暂停时施工并立即读档，可能来不及采到异常。需要留到下一次每日采样，但不需要先保存。
- 同一游戏进程中读档会继续写日志；整个游戏重启可能覆盖日志，分析时应先留存该次日志。
- 若游戏已自动重新计算，诊断读取本身也可能影响懒计算时机，不能把未复现当作问题不存在。
- 2026-09-07 已取得玩家新开局的实际运行日志，确认国家和地区各接口均输出有效数据。最初使用方括号包围的日志前缀被本地化解释器吞掉，已改为普通文本；旧日志可搜索 `GER_SUMMARY` 或 `stage=2 state=`，数据本身不受影响。

## 2026-09-07 本次实测证据

游戏时间 2060.01.01.23 和 2060.01.02.23 均记录：

```text
GER_SUMMARY country_civ=5 country_mil=5 free_civ=3 state_civ=6 state_mil=6 healthy_civ=6 healthy_mil=6
```

- 地区 50：新增军工 1，完好 1；德国拥有并控制，德国核心。
- 地区 72：新增民工 1，完好 1；德国拥有并控制，德国核心。
- 首都 64：仍为原有的民工 5、军工 5，全部完好。
- 三地 `local_factories=0.1`、污染 0、安全 100、重建 100。
- 初始及 GFCC 初始化后的国家与地区数量均为 5/5；差异出现在本局建造后。

因此已排除“只有顶栏文本不刷新”，本次新增建筑也不存在损坏或非核心占领。仍不能仅凭此确定 GFCC 是根因。

已尝试的最小干预：对地区 50 调用现有的 `GFCC_area_security_effects_3`，按当前安全度移除并重新挂载同一个安全度修正。用户提供了命令进入执行流程的控制台回显；随后至游戏时间 2060.01.06.23，国家统计仍为 5/5，地区仍为 6/6。此刷新办法未解决问题，不作为修复方案。

## 定位到的缺失：国家没有开局 OOB

本地代码核对结果：

1. 项目 `descriptor.mod` 和实际启动使用的 `APDC.mod` 都设置了 `replace_path="history/units"`，屏蔽原版 OOB。
2. 修改前项目不存在 `history/units` 目录。
3. 修改前德国国家历史没有 `oob`、`set_oob` 或 `load_oob`，其余国家历史也未发现这些入口。
4. 安装版本的原版德国在国家历史通过 `set_oob` 注册开局 OOB；随游戏附带的 `effects_documentation.md` 对 `set_oob` 的说明是注册开局加载的 OOB，而不是运行中反复加载。

已有同类问题的第一手模组实测报告：

- [Factory Count Lagging Behind](https://www.reddit.com/r/hoi4modding/comments/1dn86fq/)：发帖者确认新增国家工厂统计延迟，切换国家后更新；补充 OOB 后解决。
- [(modding) Effects not aplying after completing focus](https://www.reddit.com/r/hoi4modding/comments/1g4ngyx/)：报告新增工厂和效果在保存读档后才出现，回复指出需要 OOB。

这是已确认的项目初始化缺失。用户已实测并确认德国补齐 OOB 后问题解决；其他国家采用相同入口，已完成引用和原有历史内容保留检查，但未逐国进行游戏实测。引擎内部实现并不可见，不将其具体内部调用机制表述为已查阅源代码的事实。

### 已落地的针对性修改

- 在 `history/countries/GER - Germany.txt` 添加 `set_oob = "APDC_empty"`。
- 新建 `history/units/APDC_empty.txt`，包含空的 `units` 块和仅写一行日志的 `instant_effect`。
- 不恢复原版军队、不新增编制/部队/装备/生产线/工厂，不修改 GFCC 修正。
- 保留德国首都先前按用户要求添加的 5 民工、5 军工。
- 德国经用户确认有效后，按用户要求为其余 348 份国家历史补齐相同入口，共覆盖 349 份文件（包括预留国家）；德国原有入口保持不变。当前项目国家标签表中的全部 283 个标签均有对应历史文件并已覆盖。
- 逐文件确认仅新增共享 OOB 入口和说明注释；去除新增头部、统一换行符后，全部国家历史与修改前的 SHA-256 汇总一致。
- 将来编写某国实际 OOB 时，应将该国的 `set_oob` 改为实际 OOB 文件名，不必再同时加载空 OOB。

### 修复后的验收依据

完全重启游戏后的德国新开局，应出现 `APDC_FACTORY_INIT: empty OOB loaded for GER`。原先 5/5 的工厂各新增一座后，国家统计应随地区数量更新到 6/6，并且不需要读档。不能用旧局读档后的正常状态代替这一验收。

## 涉及文件

- `common/scripted_effects/APDC_factory_diagnostics.txt`：只读采样和日志。
- `common/on_actions/APDC_factory_diagnostics_on_actions.txt`：德国每日采样。
- `common/on_actions/GFCC_area_se_up.txt`：仅插入前后采样，保留原初始化逻辑。

诊断结束后，可移除上述两份新增脚本和 GFCC 文件中两处采样块；不要删除 GFCC 原有初始化代码。此前德国首都的 5 座民工、5 座军工保持不变。
